我一开始接触 MCP 和 Agent Skills 时，容易把它们都理解成“让 AI 变得更强的插件”。后来真正把它们放到 AI 应用开发流程里，我才发现，它们解决的是两个不同层面的问题。

说白了，MCP 主要解决“AI 怎么连接外部工具和数据”，Agent Skills 主要解决“AI 应该怎样完成一类重复任务”。一个更像统一接口，一个更像可复用的工作方法。

## MCP 解决连接问题

如果没有统一协议，AI 客户端想访问不同服务，就要为每个服务单独写一套适配。MCP 把连接方式抽象成相对统一的 Host、Transport 和 Server：客户端负责发起调用，传输层负责传递消息，Server 负责暴露工具、资源或提示词。

这里有一个容易误解的地方：Server 不一定是远程服务器。它可以运行在本地进程、容器或远程主机上。是否联网，也不由“MCP Server”这个名字决定，而要看它内部实际访问了什么。

## Agent Skills 解决能力封装问题

Skill 更接近一套可复用的工作说明。它可以包含任务规则、脚本、参考资料和输出要求，让 AI 在遇到相似问题时按需读取，而不是每次从零开始理解一长段提示词。

我现在把 Skill 理解成三层：先用描述让 AI 知道什么时候需要它，再由 `SKILL.md` 规定工作方式，最后按需要调用脚本和参考资料。这样既能保持能力可检查，也能避免把所有细节一次性塞进上下文。

## 两者怎样配合

在一个真实应用里，可以让 Skill 规定“先读取项目状态，再调用工具，最后人工验收”的流程，再让 MCP 提供查询文件、读取数据库或执行某个动作的接口。

但它们都不能替代判断。MCP 只负责把工具接进来，Skill 只负责把方法保存下来。权限边界、数据流向和执行结果仍然要由人检查。

## 我得到的实际结论

AI 应用工程化不只是把模型接上去。还要考虑工具怎么连接、能力怎么复用、权限怎么限制、结果怎么验证。MCP 和 Agent Skills 的价值，正是在这些连接和流程问题上减少重复工作。

我目前还没有把它们包装成复杂的多智能体系统。对我来说，更实际的用法是：先把一类任务拆清楚，再决定它需要一个工具接口，还是一套可复用的工作流程。
